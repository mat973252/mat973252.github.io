Agent 发出一个写请求，外部服务可能已经完成操作，但进程在保存结果前退出了。再次启动时，直接重试可能造成重复操作；把它认作失败，也可能与事实不符。

[Relay](https://github.com/mat973252/Relay) 为外部操作记录执行状态。结果无法确认时保留 `UNKNOWN`，通过只读核对获取证据，再决定是否能够确认。

## 两种退出，两种结果

2026 年 10 月 5 日，在专用测试仓库完成了一次真实 GitHub API 与受控客户端故障矩阵。测试对象是合成仓库变量，后续恢复步骤只查询，不重新提交。

**案例 A：提交前退出。** 写请求还没有交给网络调用，进程就退出了。新进程查询得到 404，记录继续保持 `UNKNOWN`；没有自动补发，也没有把一次查询结果直接改写为失败。

**案例 B：创建后退出。** GitHub 已返回创建成功，客户端随后退出。查询被阻断或返回的身份在客户端被替换时，记录保持 `UNKNOWN`；可用的查询精确匹配计划后，状态变为 `CONFIRMED`。同机并发竞争者被工作区锁拒绝，终态读取使用已记录的结果。

## 这次实验留下了什么证据

八步矩阵共记录 **12 次 fetch GET、1 次 fetch POST**。随后分别只读检查本地 journal 和远端对象，确认两条历史完整：一条仍为 `UNKNOWN`，另一条经核对达到 `CONFIRMED`。

这些是客户端调用计数，不能据此推断外部服务的历史执行次数。查询阻断与身份不符由客户端注入，也不代表 GitHub 本身发生了故障。

## 目前的边界

截至本文发布，公开版本为 **v0.1.1**；这次矩阵使用的 R4 改动仍是本地未发布成果。上述文字是实验摘要，公开安装包尚不包含这个测试入口。

实验覆盖同机锁与固定的受控场景，尚未证明跨主机生产恢复或独立开发者采用。RelayMuse 是关联的 Agent 实验线：真实模型调用配合本地合成操作验证恢复路径，尚无独立发布版本。

恢复时最有用的动作，有时就是保留不确定性，等待足够明确的证据。
